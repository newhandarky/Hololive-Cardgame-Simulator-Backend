# 併發鎖策略與效能優化

## 概述

本文件定義對戰系統的併發控制策略，確保多玩家同時操作時的資料一致性與系統效能。

---

## 1. 併發情境分析

### 1.1 常見併發情境

| 情境 | 發生頻率 | 風險等級 | 策略 |
|-----|---------|---------|------|
| 雙方玩家同時執行動作 | 低（回合制） | 低 | 樂觀鎖 |
| 同一玩家多次快速點擊 | 高 | 中 | 前端防抖 + 樂觀鎖 |
| 對戰初始化時的資料競爭 | 中 | 高 | 悲觀鎖 |
| 狀態版本不一致 | 中 | 中 | 版本號檢查 |
| WebSocket 訊息亂序 | 低 | 中 | 訊息序號 |

---

## 2. 鎖策略選擇

### 2.1 樂觀鎖（Optimistic Locking）

#### 適用情境

- **一般動作執行**（出場、使用アーツ、結束回合等）
- **衝突機率低**的操作
- **讀多寫少**的場景

#### 實作方式

使用 `@Version` 欄位（JPA 樂觀鎖）：

```java
@Entity
@Table(name = "matches")
public class Match {
    
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    
    // ⚠️ 版本號欄位
    @Version
    private Long version;
    
    private String status;
    private String currentPhase;
    private Integer turnNumber;
    
    // ... 其他欄位
}
```

#### 動作執行範例

```java
@Service
public class MatchService {
    
    @Transactional
    public ActionResult executeAction(Long matchId, Action action) {
        // 1. 讀取對戰（帶 version）
        Match match = matchRepository.findById(matchId)
            .orElseThrow(() -> new MatchNotFoundException());
        
        // 2. 執行動作（修改狀態）
        // ...
        
        // 3. 儲存（JPA 自動檢查 version）
        try {
            matchRepository.save(match);  // 若 version 不一致，拋出 OptimisticLockException
            return ActionResult.success(stateChanges);
        } catch (OptimisticLockException e) {
            // 併發衝突，重試
            return ActionResult.error("LOCK_CONFLICT", "併發衝突，請重試");
        }
    }
}
```

#### 優點

- 無需額外鎖定資源
- 效能高
- 適合大多數場景

#### 缺點

- 衝突時需要重試
- 不適合高衝突場景

---

### 2.2 悲觀鎖（Pessimistic Locking）

#### 適用情境

- **對戰初始化**（洗牌、設置起手）
- **加入房間**（避免超過 2 人）
- **關鍵狀態變更**（勝負判定）

#### 實作方式

使用 `SELECT ... FOR UPDATE`：

```java
@Repository
public interface MatchRepository extends JpaRepository<Match, Long> {
    
    @Lock(LockModeType.PESSIMISTIC_WRITE)
    @Query("SELECT m FROM Match m WHERE m.id = :matchId")
    Optional<Match> findByIdForUpdate(@Param("matchId") Long matchId);
}
```

#### 加入房間範例

```java
@Service
public class MatchService {
    
    @Transactional
    public void joinMatch(Long matchId, Long userId, JoinMatchRequest request) {
        // 1. 悲觀鎖鎖定該對戰（其他人無法同時加入）
        Match match = matchRepository.findByIdForUpdate(matchId)
            .orElseThrow(() -> new MatchNotFoundException());
        
        // 2. 檢查是否已滿
        if (match.getPlayerBId() != null) {
            throw new RoomFullException("房間已滿");
        }
        
        // 3. 加入
        match.setPlayerBId(userId);
        match.setStatus("INITIALIZING");
        matchRepository.save(match);
        
        // 4. 初始化對戰
        initializeMatch(match, request);
    }
}
```

#### 優點

- 確保資料一致性
- 適合高衝突場景

#### 缺點

- 鎖定期間其他交易必須等待
- 可能造成死鎖（需注意鎖定順序）
- 效能較樂觀鎖差

---

### 2.3 分散式鎖（Redis Lock）

#### 適用情境

- **跨伺服器的資源競爭**（例如：房間代碼產生）
- **限流控制**（例如：單一玩家建立房間數量限制）

#### 實作方式

使用 Redisson：

```java
@Service
public class MatchService {
    
    @Autowired
    private RedissonClient redissonClient;
    
    public String generateUniqueRoomCode() {
        RLock lock = redissonClient.getLock("room-code-generation");
        
        try {
            // 嘗試獲取鎖（等待 10 秒，鎖定 30 秒）
            if (lock.tryLock(10, 30, TimeUnit.SECONDS)) {
                try {
                    // 生成唯一房間代碼
                    String roomCode;
                    do {
                        roomCode = RandomStringUtils.randomAlphanumeric(6).toUpperCase();
                    } while (matchRepository.existsByRoomCode(roomCode));
                    
                    return roomCode;
                } finally {
                    lock.unlock();
                }
            } else {
                throw new RuntimeException("無法取得鎖，請稍後重試");
            }
        } catch (InterruptedException e) {
            throw new RuntimeException("鎖定過程被中斷", e);
        }
    }
}
```

## 3. 併發策略總覽

| 動作 | 策略 | 理由 |
|-----|------|------|
| 建立對戰 | 分散式鎖（房間代碼） | 避免重複代碼 |
| 加入對戰 | 悲觀鎖 | 避免超過 2 人 |
| 對戰初始化 | 悲觀鎖 | 避免重複初始化 |
| 執行動作（一般） | 樂觀鎖 | 衝突機率低 |
| 使用アーツ | 樂觀鎖 | 回合制，不會同時執行 |
| 結束回合 | 樂觀鎖 | 只有當前玩家能執行 |
| 勝負判定 | 悲觀鎖 | 確保只判定一次 |
| 投降 | 樂觀鎖 | 衝突機率低 |

## 4. 前端防抖與節流

### 4.1 防抖（Debounce）

避免玩家快速點擊導致重複請求：

```typescript
import { useCallback, useRef } from 'react';

export const useDebounce = <T extends (...args: any[]) => void>(
  callback: T,
  delay: number
) => {
  const timeoutRef = useRef<NodeJS.Timeout | null>(null);

  return useCallback((...args: Parameters<T>) => {
    if (timeoutRef.current) {
      clearTimeout(timeoutRef.current);
    }
    
    timeoutRef.current = setTimeout(() => {
      callback(...args);
    }, delay);
  }, [callback, delay]);
};

// 使用
const handleUseArt = useDebounce((holomemId, artId, targetId) => {
  sendAction({ actionType: 'USE_ART', payload: { holomemId, artId, targetId } });
}, 300);  // 300ms 內只能執行一次
```

---

### 4.2 節流（Throttle）

限制動作執行頻率：

```typescript
import { useCallback, useRef } from 'react';

export const useThrottle = <T extends (...args: any[]) => void>(
  callback: T,
  delay: number
) => {
  const lastCallRef = useRef<number>(0);

  return useCallback((...args: Parameters<T>) => {
    const now = Date.now();
    if (now - lastCallRef.current >= delay) {
      lastCallRef.current = now;
      callback(...args);
    }
  }, [callback, delay]);
};
```

---

### 4.3 按鈕禁用狀態

```typescript
const [isActionPending, setIsActionPending] = useState(false);

const handleAction = async () => {
  if (isActionPending) return;  // 避免重複執行
  
  setIsActionPending(true);
  try {
    await sendAction(action);
  } finally {
    setIsActionPending(false);
  }
};

return (
  <button onClick={handleAction} disabled={isActionPending}>
    {isActionPending ? '執行中...' : '使用アーツ'}
  </button>
);
```

## 6. Redis 快取策略

### 6.1 快取對戰狀態

```java
@Service
public class MatchCacheService {
    
    @Autowired
    private RedisTemplate<String, MatchState> redisTemplate;
    
    private static final String CACHE_PREFIX = "match:state:";
    private static final long CACHE_TTL = 300;  // 5 分鐘
    
    public MatchState getMatchState(Long matchId) {
        String key = CACHE_PREFIX + matchId;
        MatchState cached = redisTemplate.opsForValue().get(key);
        
        if (cached != null) {
            return cached;
        }
        
        // Cache miss，從資料庫讀取
        MatchState state = buildMatchStateFromDatabase(matchId);
        redisTemplate.opsForValue().set(key, state, CACHE_TTL, TimeUnit.SECONDS);
        
        return state;
    }
    
    public void invalidateCache(Long matchId) {
        String key = CACHE_PREFIX + matchId;
        redisTemplate.delete(key);
    }
}
```

---

### 6.2 快取策略

| 資料類型 | 快取策略 | TTL | 失效時機 |
|---------|---------|-----|---------|
| 對戰狀態 | Cache-Aside | 5 分鐘 | 動作執行後 |
| 卡片定義 | 預載入 | 永久 | 伺服器重啟 |
| 玩家資料 | Cache-Aside | 10 分鐘 | 更新後 |
| 房間代碼 | Write-Through | 1 小時 | 對戰結束 |

## 7. 批次查詢優化

### 7.1 避免 N+1 查詢

❌ **不好的做法**：

```java
List<MatchHolomem> holomems = matchHolomemRepository.findByMatchId(matchId);
for (MatchHolomem holomem : holomems) {
    List<CheerCard> cheers = cheerRepository.findByHolomemId(holomem.getId());
    // N+1 查詢問題
}
```

✅ **好的做法**：

```java
@Query("SELECT mh FROM MatchHolomem mh " +
       "LEFT JOIN FETCH mh.cheers " +
       "WHERE mh.matchId = :matchId")
List<MatchHolomem> findByMatchIdWithCheers(@Param("matchId") Long matchId);
```

---

### 7.2 批次載入

```java
// 一次性載入所有必要資料
MatchState buildMatchState(Long matchId) {
    Match match = matchRepository.findById(matchId).orElseThrow();
    List<MatchPlayer> players = matchPlayerRepository.findByMatchId(matchId);
    List<MatchHolomem> holomems = matchHolomemRepository.findByMatchIdWithCheers(matchId);
    List<MatchCard> cards = matchCardRepository.findByMatchId(matchId);
    
    return MatchState.builder()
        .match(match)
        .players(players)
        .holomems(holomems)
        .cards(cards)
        .build();
}
```

## 8. 連線池優化

### 8.1 HikariCP 配置

```yaml
spring:
  datasource:
    hikari:
      maximum-pool-size: 20  # 最大連線數
      minimum-idle: 5        # 最小閒置連線數
      connection-timeout: 30000  # 連線超時（30 秒）
      idle-timeout: 600000   # 閒置超時（10 分鐘）
      max-lifetime: 1800000  # 連線最大存活時間（30 分鐘）
```

---

### 8.2 連線數估算

```
最大連線數 = (CPU 核心數 * 2) + 磁碟數量

例如：4 核心 + 1 磁碟 = 10 連線
但建議設定 20（考慮尖峰流量）
```

### 9.2 日誌記錄

```java
@Slf4j
@Service
public class MatchService {
    
    @Transactional
    public ActionResult executeAction(Long matchId, Action action) {
        long startTime = System.currentTimeMillis();
        
        try {
            // 執行動作
            ActionResult result = doExecuteAction(matchId, action);
            
            long duration = System.currentTimeMillis() - startTime;
            log.info("動作執行成功: matchId={}, actionType={}, duration={}ms", 
                     matchId, action.getType(), duration);
            
            return result;
        } catch (OptimisticLockException e) {
            log.warn("併發衝突: matchId={}, actionType={}", matchId, action.getType());
            throw new LockConflictException("併發衝突，請重試");
        }
    }
}
```

## 總結

本文件定義了併發鎖策略與效能優化方案，包括：

1. **樂觀鎖**：用於一般動作（衝突機率低）
2. **悲觀鎖**：用於關鍵操作（對戰初始化、加入房間）
3. **分散式鎖**：用於跨伺服器資源競爭
4. **前端防抖／節流**：避免重複請求
5. **Redis 快取**：減少資料庫壓力
6. **批次查詢**：避免 N+1 問題
7. **監控與日誌**：追蹤效能與錯誤

遵循這些策略可確保系統在高併發情境下的穩定性與效能。
