# 0423 架構拆分計畫

## 背景

目前後端主要壓力集中在三個檔案：

- `MatchActionServiceIntegrationTest.java`：約 3.5 萬行，集中 300 多個整合測試。
- `MatchEffectService.java`：約 1.45 萬行，混合 effect dispatch、文字解析、trigger、modifier、damage、search、dice、特殊卡例外。
- `MatchActionService.java`：約 1 萬行，混合 action orchestration、phase flow、pending decision、攻擊流程、DB 讀寫與部分規則判斷。

這些檔案不是單純「太長」，而是職責邊界已經混在一起。直接大規模搬動會提高功能回歸風險，因此本計畫採取小步、可驗證、可回滾的拆分策略。

## 核心原則

1. 外部 API 先不動。
   - Controller 呼叫的 service method 簽名先保持不變。
   - 前端 request / response 行為先保持不變。

2. DB schema 先不動。
   - 架構拆分階段不同時做 migration 調整。
   - SQL 行為改動必須有明確測試覆蓋後才進行。

3. 先拆測試，再拆 production。
   - `MatchActionServiceIntegrationTest` 是目前最重要的保護網。
   - 先把測試 helper 與測試檔依功能拆開，降低後續 production refactor 的風險。

4. 先保留 facade。
   - `MatchActionService` 與 `MatchEffectService` 初期仍作為外部入口。
   - 內部逐步委派給較小的 handler / service。

5. 一次只切一個職責。
   - 不同時改 effect parser、action flow、DB schema 與測試結構。
   - 每一步都必須能獨立驗證。

## 禁止事項

- 不一次把 `MatchActionService` 拆成大量服務。
- 不邊拆邊改卡片規則行為。
- 不用卡號當主要架構邊界。
- 不把大量 private method 原封不動搬成新的巨大類別。
- 不在缺少測試保護的情況下重寫 damage / down / life 流程。

## 第一階段：測試拆分

目標：不改 production 行為，先降低測試檔維護成本。

建議順序：

1. 建立共用測試支援類別。
   - 目標檔案：`MatchIntegrationTestSupport`
   - 放置內容：
     - 建立對戰 fixture。
     - 插入測試卡片。
     - 設定手牌、牌組、cheer、holopower。
     - 常用 zone / stage 查詢。

2. 將 `MatchActionServiceIntegrationTest` 依功能拆檔。
   - `MatchOpeningFlowIntegrationTest`
   - `MatchTurnFlowIntegrationTest`
   - `MatchSupportActionIntegrationTest`
   - `MatchBloomCollabIntegrationTest`
   - `MatchAttackArtIntegrationTest`
   - `MatchOfficialCardRegressionIntegrationTest`

3. 每次搬移一小批測試。
   - 搬移後先跑被搬出的測試類別。
   - 再跑原本仍留在 `MatchActionServiceIntegrationTest` 的測試。
   - 最後跑完整 smoke / integration suite。

驗收條件：

- 測試行為不變。
- 測試資料準備邏輯集中到 support 類別。
- `MatchActionServiceIntegrationTest` 行數逐步下降。

## 第二階段：MatchEffectService 拆分

目標：保留 `MatchEffectService` public method，先拆內部可獨立驗證的 effect 能力。

建議順序：

1. `AttachedSupportEffectService`
   - HP bonus
   - art bonus
   - incoming damage reduction
   - conditional trigger preview

2. `PassiveGiftModifierService`
   - art bonus
   - damage reduction
   - HP bonus
   - cheer cost reduction

3. `EffectDiceService`
   - dice roll count
   - dice condition
   - fixed dice / reroll 特例

4. `EffectSearchService`
   - search candidate loading
   - criteria filtering
   - selected card validation

5. `DamageEffectExecutor`
   - 最後才拆。
   - damage 牽涉 down event、life、trigger、damage prevention，回歸風險最高。

驗收條件：

- `MatchEffectService` public API 不變。
- 原測試與 official smoke 覆蓋全部通過。
- 新 service 有清楚單一職責。

## 第三階段：MatchActionService 拆分

目標：保留 `MatchActionService` 作為 action facade，逐步抽出 action handler。

建議順序：

1. `TurnFlowService`
   - draw turn
   - send cheer
   - advance phase
   - end turn

2. `PendingDecisionService`
   - pending decision 建立、讀取、resolve、follow-up payload。

3. `SupportPlayActionHandler`
   - support 使用流程。

4. `BloomActionHandler`
   - bloom 驗證、stack、trigger。

5. `AttackArtActionHandler`
   - 最後才拆。
   - attack art 牽涉最多卡片規則與 trigger，必須等測試拆分完成後再動。

驗收條件：

- `MatchActionService` method 簽名不變。
- handler 只處理 orchestration，不複製大量 SQL 與 parser 邏輯。
- 每個 handler 拆出後都跑對應 integration test。

## 驗證策略

每個小步至少跑：

```bash
./mvnw -q -Dtest=OfficialCardSmokeCoverageIntegrationTest test
```

如果改到 action flow，額外跑：

```bash
./mvnw -q -Dtest=MatchActionServiceIntegrationTest test
```

如果只搬測試 helper，先跑被搬動的測試類別，再跑完整對應 suite。

最後合併前必跑：

```bash
./mvnw -q test
git diff --check
```

## 分支策略

本輪工作分支：

```text
refactor/split-match-services
```

`main` 保持可用狀態。架構拆分完成並通過驗證後，再由使用者決定是否合併回 `main`。
