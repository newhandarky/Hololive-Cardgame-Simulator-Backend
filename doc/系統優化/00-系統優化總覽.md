## 三、新優化原則

### 1. Legacy facade 設預算，不再成長

- 不在 `MatchActionService`、`MatchEffectService` 新增新的 feature responsibility。
- 新 action 先進 command/handler/application boundary，再由 legacy adapter 暫時委派。
- 每完成一個 vertical slice，必須移除至少一段舊 orchestration 或一個不再需要的依賴。
- 只新增 delegate、但沒有刪除舊責任，不算完成拆分。

### 2. 規則只能有一個權威來源

- command validation、ActionCapabilities 與 NPC 不得各自維護 phase/pending/cost/target 判斷。
- DB-backed rule 透過具名 query/fact service；pure rule 以 table-driven test 驗證。
- 前端只做顯示、選擇與預覽，不複製伺服器核心合法性。

### 3. 先建立 seam，再搬移程式碼

- 保留 REST、WebSocket 與 DB 相容性。
- 以 controller → command handler → rule/fact → mutation/event → projection 為遷移單位。
- package move、規則修正、公開契約與 DB migration 分開提交。

### 4. 高風險引擎改造延後

- `MatchEffectService` 不做一次性完整搬移。
- typed EffectPrimitive、timing queue 與 deterministic RNG 必須建立在 PendingChoice、state version 與 scenario harness 之後。
- 新卡若仍需 legacy parser，必須有明確 adapter 與 coverage 指標，不直接擴充主 service。
