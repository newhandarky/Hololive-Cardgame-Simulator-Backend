# 系統優化總覽

更新日期：2026-04-28
定位：`hololive-cardgame-backend` 系統優化主入口
用途：彙整目前專案最急迫的結構問題、優先順序、分階段文件入口與執行原則。

---

## 一、目前判斷

目前後端最急迫的問題不是單一 bug，而是兩個核心服務持續膨脹：

- `src/main/java/com/hololive/cardgame/service/MatchEffectService.java`
- `src/main/java/com/hololive/cardgame/service/MatchActionService.java`

這兩個檔案已同時承擔：

- facade 入口
- 規則判斷
- pending interaction / decision 流程
- SQL 查詢與資料更新
- 特殊卡例外處理
- 測試回歸主戰場的耦合責任

若在這個狀態下持續直接補卡、補規則、補 trigger，後續每次修改都會碰到相同的大檔案，回歸風險和閱讀成本會持續上升。

因此本輪系統優化的主軸是：

1. 先拆責任邊界，再談模式升級。
2. 先保留既有 facade 與 API，不做 big bang rewrite。
3. 每一步都要能用既有整合測試與 smoke 流程驗證。

---

## 二、優先順序

### P0：主流程服務拆分

1. `MatchEffectService` 拆成可維護的 effect family / trigger 協調模組
2. `MatchActionService` 拆成 action entry / decision resolution / turn-phase 協調模組

### P1：部署前阻塞項

1. `card-admin` 權限保護
2. LIFF 真實登入驗證

### P2：維護性補強

1. `DeckService` 職責收斂
2. `HardNpcService` 子模組化
3. 文件與雜訊檔治理
4. effect JSON 結構驗證補強

## 四、架構判斷原則

### 1. 不直接用卡號當拆分邊界

卡號會持續增加，若以單卡或小批卡號為主軸拆分，最後只會把 God Class 變成一堆依卡號分類的 God Handler。

### 2. 先按流程責任拆，不先按設計模式命名

本專案可以逐步收斂到 registry / handler / command 形式，但前提是先把責任切乾淨。否則只是把複雜度搬家。

### 3. 初期保留 facade

`MatchEffectService` 與 `MatchActionService` 先保留對外入口，內部改為委派。這能降低 controller、NPC、測試與其他 service 同步改動的成本。

### 4. 先拆 production 內部，再考慮 package 重組

不要一開始就改大量 package 路徑或 class 命名。先讓 responsibility 下降、測試穩定，再做目錄美化。
