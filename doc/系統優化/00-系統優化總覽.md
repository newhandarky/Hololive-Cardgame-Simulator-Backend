---

## 一、目前狀態

本輪後端優化的主線是降低 production god class 複雜度，優先處理 `MatchEffectService`，再回到 `MatchActionService`。目前已完成一批連續、可驗證、可回退的 effect execution service extraction。

目前仍需關注的大檔：

- `src/main/java/com/hololive/cardgame/service/MatchEffectService.java`：`9,831` 行。
- `src/main/java/com/hololive/cardgame/service/MatchActionService.java`：`6,099` 行。
- `src/test/java/com/hololive/cardgame/service/MatchActionServiceIntegrationTest.java`：`32,299` 行。

本輪完成後，`MatchEffectService` 已從優化初期的萬行級核心大檔逐步下降，且多個低風險 effect family 已移出主 service。後續不再以單次小 helper 為 commit 單位，而是以「相鄰責任區」為單位拆分。

## 三、下一步優化方向

### P0：繼續拆 `MatchEffectService`

建議下一批優先順序：

1. `REVEAL_TO_ARCHIVE`
   - 與剛完成的 `DISCARD_HAND` 同樣使用 criteria / candidate / zone update。
   - 風險低於 stage summon 與戰鬥類效果。
   - 建議新增 `MatchRevealToArchiveEffectExecutionService` 與 focused unit test。

2. `SUMMON_TO_STAGE`
   - 收益較高，但牽涉 stage zone、level normalization、stack 記錄與 destination 判斷。
   - 應先補 focused tests，再抽 service。

3. 暫緩戰鬥類效果
   - `DAMAGE` / `DOWN` / `HEAL` / `MOVE_ZONE` 仍屬高風險區塊。
   - 需等候選查詢類與 stage 類拆分穩定後，再以更完整測試保護進行。

### P1：回頭整理 `MatchActionService`

`MatchActionService` 目前已比 `MatchEffectService` 更穩定，但仍有 `6,099` 行。等 `MatchEffectService` 的低中風險 execution family 再收斂一批後，建議回到：

- decision resolution flow
- turn / phase lifecycle
- board action orchestration

### P2：測試巨檔治理

`MatchActionServiceIntegrationTest` 仍是最大檔案，但目前不作為主線優先處理。只有在 production 重構需要測試保護或測試定位困難時，才順手拆對應主題測試。

## 五、文件治理原則

- `00-系統優化總覽.md` 只保留目前方向、優先序與閱讀入口。
- `05-重構進度追蹤.md` 只保留目前進度摘要與近期批次，不再累積完整歷史。
- 完整歷史改放 `doc/系統優化/archive/`。
- 舊的單次開發稿與已被新文件取代的規則，歸檔到 `doc/history/archived-2026-05-25/`。
- 核心規格文件不刪除，包括 `0212-*`、REST/WebSocket/DB/對戰引擎、官方規則書、GameRoom 契約與當前 action 契約。

## 六、完成標準

本輪系統優化不以「檔案行數下降」作為唯一完成條件，而以以下四點為準：

1. `MatchEffectService` 與 `MatchActionService` 的核心責任邊界清楚。
2. 新增規則時，不必再修改同一個 God Class 的多個遠距區塊。
3. 整合測試與 smoke 驗證仍能維持既有保護力。
4. 文件入口能快速回答目前進度、下一步優先序與歷史紀錄位置。
