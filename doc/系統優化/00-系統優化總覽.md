## 一、目前狀態

本輪後端優化的主線是降低 production god class 複雜度，優先處理 `MatchEffectService`，再回到 `MatchActionService`。目前已完成一批連續、可驗證、可回退的 effect execution service extraction。

目前仍需關注的大檔：

- `src/main/java/com/hololive/cardgame/service/MatchEffectService.java`：`4,910` 行。
- `src/main/java/com/hololive/cardgame/service/MatchActionService.java`：`5,111` 行。
- `src/test/java/com/hololive/cardgame/service/MatchActionServiceIntegrationTest.java`：`32,302` 行。

本輪完成後，`MatchEffectService` 已從優化初期的萬行級核心大檔逐步下降，且多個低風險 effect family 已移出主 service。後續不再以單次小 helper 為 commit 單位，而是以「相鄰責任區」為單位拆分。

## 三、下一步優化方向

### P0：繼續 `MatchActionService` decision lifecycle

建議下一批優先順序：

1. Decision resolution service
   - AAA-231 已先抽出 `PendingDecisionStore`，集中 pending `FOR UPDATE` 載入、context JSON 映射與 resolved 更新。
   - AAA-232 已抽出 `PendingDecisionCreationService`，集中 `TURN_START`、`LIVE_START`、`DRAW_REVEAL`、`SEND_CHEER`、`CARD_SELECTION` 的 context payload 與 insert SQL。
   - AAA-233 已新增 `MatchDecisionResolutionService`，第一刀只承接 `LOOK_TOP_DECK`、`LOOK_OPPONENT_HAND` / `LOOK_HOLOPOWER`、`REORDER_DECK_BOTTOM`。
   - AAA-234 已將 `DRAW_REVEAL` resolution 搬入 `MatchDecisionResolutionService`，保留 turn cheer 判斷、main step gift follow-up 與 lifecycle confirm 行為。
   - AAA-235 已將 `SEND_CHEER` resolution 搬入 `MatchDecisionResolutionService`，保留目標驗證、來源 Cheer 驗證、`SendCheerAction` 執行、phase 更新與 action log 行為。
   - AAA-236 已將 `LIVE_START` resolution 搬入 `MatchDecisionResolutionService`，保留 pending resolved 與 `MatchTurnLifecycleService.confirmLiveStartDecision(...)` 委派。
   - AAA-237 已抽出 `SelectedCardValidationService`，讓 `MatchDecisionResolutionService` 與 `MatchActionService` 共用 selected-card sanitize / min-max / candidate validation。
   - AAA-238 已抽出 `MatchTurnStartCollabReturnService`，集中 `TURN_START` 前 COLLAB 回 BACK rested 與 HBP03-039 / フワワ中心特例。
   - AAA-239 已將 `TURN_START` resolution 搬入 `MatchDecisionResolutionService`，保留 pending resolved、collab return helper 委派與 `MatchTurnLifecycleService.confirmTurnStartDecision(...)`。
   - 下一批可評估 `CARD_SELECTION` resolution 的 focused test / helper boundary；不要直接把 `TRIGGER_EFFECT_CONFIRM` 與 `CARD_SELECTION` 混成同批。

2. Turn / phase lifecycle
   - Decision resolution service 穩定後，再回頭集中 draw / cheer / phase advance / live start 等流程。

3. Board action orchestration
   - Decision / turn flow 邊界穩定後，再整理 play support / attach cheer / board action orchestration。

### P2：`MatchActionService` 其他 flow

`MatchActionService` 目前仍有 `5,091` 行。AAA-231 / AAA-232 已先抽出 pending store 與 creation service，AAA-233 到 AAA-239 已開始擴充 `MatchDecisionResolutionService`、收斂 decision selected-card validation，並搬移 `TURN_START` decision resolution。除 P0 的 pending / decision lifecycle 外，後續仍需整理：

- decision resolution flow
- pending interaction 建立器搬移

- board action orchestration

### P3：測試巨檔治理

`MatchActionServiceIntegrationTest` 仍是最大檔案，但目前不作為主線優先處理。只有在 production 重構需要測試保護或測試定位困難時，才順手拆對應主題測試。

## 五、文件治理原則

- `00-系統優化總覽.md` 只保留目前方向、優先序與閱讀入口。
- `05-重構進度追蹤.md` 只保留目前進度摘要與近期批次，不再累積完整歷史。
- 完整歷史改放 `doc/系統優化/archive/`。
- 舊的單次開發稿與已被新文件取代的規則，歸檔到 `doc/history/archived-2026-05-25/`。
- 核心規格文件不刪除，包括 `0212-*`、REST/WebSocket/DB/對戰引擎、官方規則書、GameRoom 契約與當前 action 契約。

## 六、完成標準

本輪系統優化不以「檔案行數下降」作為唯一完成條件，而以以下四點為準：

1. `MatchEffectService` 與 `MatchActionService` 的核心責任邊界清楚。
2. 新增規則時，不必再修改同一個 God Class 的多個遠距區塊。
3. 整合測試與 smoke 驗證仍能維持既有保護力。
4. 文件入口能快速回答目前進度、下一步優先序與歷史紀錄位置。
