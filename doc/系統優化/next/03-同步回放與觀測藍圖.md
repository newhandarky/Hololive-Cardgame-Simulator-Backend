# 同步、回放與觀測藍圖

原始日期：2026-07-24
重新審閱：2026-09-03
定位：REST command、WebSocket event、state version、hidden projection 與 replay 設計

> 設計方向仍成立；執行順序改為先完成 command/choice boundary，再由 BE-005/FE-005 導入版本化同步，最後才做完整 ReplayHarness。

## 一、現況問題

目前 mutation 由 REST 完成，controller 隨後呼叫 `MatchSocketHandler.publish(...)`。WebSocket 為每個 session 重新查詢個人化完整 game state。前端為防漏訊，又在對戰中每 1.5 秒輪詢 lobby + state。

這個做法 MVP 可用，但有四個缺口：

- REST 成功、DB commit 後若 publish 失敗，client 只能等輪詢。
- payload 沒有一致 stateVersion，client 無法判斷漏了一版。
- 多數 command 沒有 idempotency key，網路重送可能重複執行。
- polling 與 WebSocket 同時寫入 React state，舊 response 可能覆蓋新 snapshot。

## 二、command envelope

所有 mutation endpoint 最終統一接受：

```json
{
  "commandId": "019...",
  "expectedStateVersion": 41,
  "payload": {}
}
```

相容期可：

- 保留具名 endpoint。
- header 傳 `X-Command-Id`、`If-Match`，或逐步擴充 body。
- 舊 client 缺欄位時由 server 產生 commandId，但不提供跨重試保證。

回應：

```json
{
  "commandId": "019...",
  "status": "ACCEPTED",
  "previousStateVersion": 41,
  "stateVersion": 42,
  "eventIds": ["evt-..."],
  "snapshotRequired": false
}
```

錯誤至少區分：

- `RULE_REJECTED`
- `STALE_STATE`
- `DUPLICATE_COMMAND`
- `MATCH_FINISHED`
- `CHOICE_REQUIRED`
- `VALIDATION_ERROR`

## 三、stateVersion 與冪等

每場 match 有單調遞增 `state_version`：

1. 鎖 match row。
2. 檢查 `expectedStateVersion`。
3. 以 `matchId + commandId` 查 accepted command。
4. 執行 mutation。
5. 寫 command/event log。
6. version + 1。
7. commit。

duplicate command：

- 若已成功，回傳原 result/version，不再執行。
- 若 payload hash 不同，回傳 `COMMAND_ID_REUSED`。
- 若前次失敗且未 commit，可依同 commandId 重試。

不要以 timestamp 當 version。

## 四、WebSocket envelope

```json
{
  "messageId": "msg-...",
  "matchId": 42,
  "type": "MATCH_STATE_CHANGED",
  "stateVersion": 42,
  "causedByCommandId": "019...",
  "serverTime": "2026-07-24T12:00:00Z",
  "payload": {
    "snapshot": {}
  }
}
```

初期維持完整 snapshot，先取得版本正確性；payload 大小或 query 成本成為瓶頸後，再引入 patch/delta。

client 規則：

- `incomingVersion <= currentVersion`：忽略。
- `incomingVersion == currentVersion + 1`：套用。
- `incomingVersion > currentVersion + 1`：標記 gap，GET snapshot。
- reconnect：帶最後版本；server 可先只回最新 snapshot。

## 五、可靠 publish

短期：

- 只在 transaction commit 後 publish。
- publish failure 記錄 metric/log。
- client 以 version gap + reconnect snapshot 修復。

中期若實測需要：

- 加 transaction outbox。
- background publisher 讀未發布 outbox。
- messageId 去重。

不在沒有漏訊量測前導入 Kafka。單機部署可先用 DB outbox。

## 六、hidden-information projection

同一 domain state 產生不同 viewer projection：

| Viewer | 可見內容 |
| --- | --- |
| 自己 | 自己手牌與允許看的暫時區域 |
| 對手 | 手牌數量、公開場面，不含 card identity |
| 觀戰者 | 雙方公開資訊；延遲/裁判模式另定 |
| 管理/測試 | 完整 state，但不得走一般 player endpoint |

projection test 必須覆蓋：

- HAND、DECK、LIFE、face-down HOLOPOWER。
- look/reveal choice 的暫時授權。
- WebSocket personalized event。
- recent action payload 不得意外帶出 hidden card ID。

## 七、replay 定位

下一階段 replay 目標是診斷與確定性驗證：

```text
InitialSnapshot
+ AcceptedCommandLog
+ ruleset/cardData/rng versions
-> ReplayHarness
-> FinalStateHash + domain events
```

若 legacy SQL mutation 尚無法由 command 重建，replay harness 可先使用 scenario fixture + command gateway，在測試 DB 執行；不要偽裝成 production event sourcing。

action/event log 最少記錄：

- commandId、actor、matchId。
- command type 與 normalized payload。
- previous/new stateVersion。
- ruleset/cardData/rng version。
- RNG outcomes。
- effect plan IDs / legacy fallback。
- accepted/rejected code。
- domain events 與 state hash（可分階段導入）。

## 八、觀測

結構化 log context：

- `matchId`
- `commandId`
- `stateVersion`
- `actorUserId`
- `actionType`
- `phase`
- `rulesetVersion`
- `cardDataVersion`
- `durationMs`

禁止記錄：

- JWT、LINE token。
- 未公開手牌內容。
- 完整私有 game state。

建議 metrics：

- command latency / rejection / conflict。
- lock wait。
- duplicate command。
- pending choice age。
- WebSocket sessions / publish failure / reconnect gap。
- snapshot payload size / projection query time。
- legacy effect usage / unsupported primitive。
- replay mismatch。

## 九、安全補強

目前 browser WebSocket 以 query parameter 傳 JWT。query 可能進入 access log、proxy log 或監控。建議分階段改成：

1. 登入後以 authenticated REST 取得短效、一次性 WS ticket。
2. WebSocket handshake 傳 ticket。
3. ticket 綁 user、match、expiry 並只可使用一次或短時間重用。

在 ticket 完成前：

- 確認 proxy/access log 不記 query。
- 降低 token TTL。
- 限制 origin。
- 不在錯誤 log 輸出完整 URI。

## 十、效能原則

- 先量測 `MatchGameStateService` query count、latency 與 payload，再決定 snapshot cache。
- card catalog 為低變動資料，可在 projection 帶必要 display metadata，或提供 batch endpoint/cache key。
- 不把 Redis 當成 canonical match state，除非另有一致性設計。
- 正常 WS 連線不輪詢；polling 只作 degraded mode 並採退避。
