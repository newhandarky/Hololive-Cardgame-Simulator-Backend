## 一、測試目標

現有測試數量充足，但分布不均：大量保護集中在 32,000 行的 `MatchActionServiceIntegrationTest` 與官方卡 smoke。下一階段要保留覆蓋力，同時讓測試對應模組邊界。

測試需回答：

- command 是否被正確接受/拒絕。
- mutation 後 state 與 invariants 是否正確。
- timing/trigger 順序是否確定。
- pending choice 是否能續接。
- projection 是否保護隱藏資訊。
- duplicate/stale command 是否安全。
- 同 seed replay 是否一致。
- 前後端 schema 是否同步。

## 二、分層策略

| 層級 | 對象 | 是否使用 DB | 重點 |
| --- | --- | --- | --- |
| Pure rule test | rule、target、cost、timing policy | 否 | 快速、表格化 |
| Primitive handler test | typed effect handler | port fake 或否 | success/failure/boundary |
| Application handler test | command pipeline | fake ports 或小型 DB | transaction output、events |
| Persistence adapter test | SQL/JPA adapter | Testcontainers | lock、constraint、mapping |
| Scenario integration | 完整 action family | PostgreSQL | state/payload/timing |
| Replay/golden test | command sequence | PostgreSQL 或 pure reducer | final hash/event sequence |
| Contract test | REST/WS/schema/projection | 可選 | compatibility/hidden data |
| Browser E2E | 兩位玩家 UI | 真後端 | happy path/reconnect/choice |

## 三、測試巨檔拆分

目標結構：

```text
src/test/java/com/hololive/cardgame/match
├── support
│   ├── MatchScenarioFixture.java
│   ├── MatchAssertions.java
│   └── CardFixtureCatalog.java
├── turn
├── board
├── attack
├── choice
├── effect
├── projection
├── concurrency
└── replay
```

規則：

- 先抽 fixture/support，再移動測試；不可同批改 production 行為。
- 依行為分類，不依原 service 名稱分類。
- test name 保留既有語意，方便 Git history。
- shared fixture 只提供 setup，不隱藏核心 assert。
- 大型官方卡 smoke 與少數深度 scenario 分開。

## 四、Scenario DSL

建立最小 DSL，避免每個測試複製 SQL：

```java
scenario()
    .withRuleset("2026-07")
    .withSeed(1234)
    .players(alice(), bob())
    .atPhase(MAIN)
    .onStage(alice(), center("HBP..."))
    .inHand(alice(), card("..."))
    .submit(alice(), playCard(...))
    .expectAccepted()
    .expectEvent(CARD_ENTERED_STAGE)
    .expectInvariantValid();
```

DSL 必須呼叫正式 command gateway，不可直接繞過規則修改 production table；只有 fixture 建立初始狀態可直接寫 DB。

## 五、卡牌遊戲特有測試

### Invariant/property

- card instance 不重複 zone。
- zone capacity。
- turn/phase 單調合法。
- resource/cost 不為負。
- blocking choice 阻擋其他 command。
- duplicate command state hash 不變。
- hidden projection 不洩漏。

### Timing

- 同時 trigger 的 active player / non-active player 順序。
- once-per-turn usage。
- damage prevention -> damage -> down -> life loss -> finish。
- Bloom/Collab/enter trigger 與 follow-up choice。

### Random

- 固定 seed 得到固定 shuffle/dice。
- cursor 消耗次數符合預期。
- replay 使用同 algorithm version。

### Data coverage

- 每個 published primitive 至少一組 handler unit test。
- 每個 effect family 有 representative deep scenario。
- 每次官方卡匯入重跑 coverage-gap 報表。
- unsupported/legacy 卡數只能在明確核准下增加。

## 六、契約測試

需要固定：

- command request/response envelope。
- `GameState`、`ActionCapabilities`、`PendingChoice`。
- WebSocket message envelope。
- error code 與 HTTP status。
- player/opponent/spectator projection。

建議由後端產生 OpenAPI 或 JSON Schema，前端型別由 schema 產生或至少以 fixture contract test 驗證。不要再由兩邊手寫後只靠人工文件同步。

## 七、品質閘門

### 文件批次

```bash
git diff --check
```

### 一般後端批次

```bash
./mvnw -q -DskipTests compile
./mvnw -q -Dtest=<FocusedTest> test
git diff --check
```

### command/rule/effect 批次

額外要求：

- 新 pure unit tests。
- 至少一個 focused integration scenario。
- GitNexus impact report。
- `gitnexus_detect_changes()`。
- 若有 ActionCapabilities，新增「enabled capability 與相同 fixture command 可成功」的 parity test。
- 完成的 vertical slice 必須指出移除的 legacy orchestration、重複規則或依賴。

### DB/API/核心規則批次

額外要求：

- migration rollback/forward 說明。
- contract test。
- concurrency 或 idempotency test。
- 代表性官方卡 smoke。
- 影響與回滾說明。

## 八、CI 建議

分成：

- `fast`：compile、unit、architecture、frontend lint/build/unit。
- `match-focused`：按 turn/board/attack/effect/choice 分組。
- `official-card-smoke`：可較慢。
- `full-integration`：PostgreSQL/Testcontainers。
- `browser-e2e`：主要 happy path、choice、reconnect。

PR 必跑 fast + affected group；主分支或排程跑全量。不要讓每個小 helper 重構都等待全部官方卡深測，但高風險 timing/effect 必須跑對應 bucket。

前端在 FE-000 完成前不得把 lint failure 設為允許失敗；若需要分批修復，必須在 FE-000 work item 內列出逐步歸零的固定數量與期限。

## 九、完成定義

- 沒有新增只存在 God Class 巨檔中的測試。
- 新模組有對應 test package。
- replay mismatch 能輸出第一個不同 stateVersion/event。
- contract fixture 可被前端測試使用。
- 測試失敗訊息包含 matchId/commandId/phase，不需先讀大量 SQL 才能定位。
