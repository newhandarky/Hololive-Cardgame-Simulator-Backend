# 架構現況與決策

更新日期：2026-09-03
定位：下一階段重構的 current-state baseline 與架構決策

> 本文件的架構判斷於 2026-09-03 重新校正；實際執行順序以 `05-遷移路線與工作包索引.md` 為準。

## 一、現況架構

### 後端

目前是單一 Spring Boot application：

```text
HTTP MatchController
  -> MatchActionService / LobbyMatchService / HardNpcService
  -> JPA Repository + JdbcTemplate
  -> PostgreSQL
  -> MatchSocketHandler 重新查詢個人化 GameState 後廣播
```

值得保留的基礎：

- 每個對戰 action 已有具名 REST endpoint，對 API 使用者清楚。
- `findByIdForUpdate` 與 transaction 已提供 per-match 悲觀鎖的基礎。
- 已有 `match_actions`、deck snapshot、pending decision 與個人化 game-state projection。
- Bloom、Collab、Play Card、Attach Cheer、End Turn、Attack 已出現 validator、resolver、application、event、trigger 等橋接式拆分。
- `game/action` 已有 `AtomicAction`、`EffectResolver`、`GameActionExecutor` 雛形。
- 官方卡 smoke、深度整合測試與效果族群報表的保護力高。

主要結構問題：

| 問題 | 現況證據 | 開發影響 |
| --- | --- | --- |
| 應用流程集中 | `MatchActionService` 約 5,003 行、約 157 方法、75 個依賴欄位 | 新 action 或 pending 流程容易跨區修改 |
| 效果語意集中 | `MatchEffectService` 約 4,910 行、約 140 方法、48 個依賴欄位 | 卡片特例、parser、SQL、summary 與執行互相耦合 |
| package 無法表達模組 | `service/` 約 311 檔 | 看檔名才能推斷責任，依賴方向無法自動防守 |
| persistence 滲入規則 | 多個 service 與 `GameActionExecutor` 直接執行 SQL | 規則難以純單測、回放與替換 |
| 動態 payload 過多 | `Map<String, Object>`、JSON string、effect text regex | 編譯器無法保護欄位與分支完整性 |
| action contract 不一致 | 多數 action 無 commandId / expectedVersion；End Turn 已局部有 idempotency | 重送、雙擊與斷線恢復難統一 |
| event 不是可靠事件流 | action log、DB mutation、WebSocket publish 各自存在 | commit 後漏推播或重播不一定可重建 |
| NPC 直接編排 service | `HardNpcService` 約 1,225 行 | NPC 複製 phase 與合法性規則 |

### 前端

目前是小型 React/Vite SPA，但責任高度集中：

```text
App.tsx
  -> auth / users / decks / backgrounds / lobby / match session
  -> REST action handlers
  -> WebSocket snapshot
  -> 1.5s/2s polling fallback
  -> GameRoomScreen props
```

主要問題：

- `App.tsx` 約 1,235 行，持有跨 feature session 與所有 action handler。
- `GameRoomScreen.tsx` 約 1,942 行，同時負責規則推導、資料補查、view-model、modal 與渲染。
- `api.ts` 約 622 行，HTTP client、所有 DTO 與所有 feature endpoint 混在同檔。
- `App.css` 約 1,626 行，缺少 feature 樣式邊界。
- 對戰畫面在 client 重複判斷 Bloom、開場、phase、turn draw/cheer 等合法性。
- 對戰中 WebSocket 已推完整 snapshot，仍每 1.5 秒發出兩個 GET 作常態補償。
- 前端 FE-000 已建立 Vitest 與 5 個 pure selector tests；component/E2E 基線仍待後續工作包補齊。
- 前端 production build 與 lint 已通過（0 errors、0 warnings），原 GameRoom derived state/effect/memo 問題已在 FE-000 收斂。
- 卡牌 metadata 不在 game projection 中，GameRoom 會針對畫面上的 unique card ID 個別取得 detail。

## 二、核心判斷

### 1. 需要重構，但不需要重寫

現有規則覆蓋、migration 與整合測試很有價值。重寫會同時失去大量隱性規則與回歸保護。正確策略是：

- 保留 API facade 與資料表。
- 在 facade 後建立新 application boundary。
- 以一條 action flow 為單位搬移。
- 用雙軌 adapter 保持舊流程可回滾。

### 2. 目標是 modular monolith

目前沒有證據需要 microservices。對戰交易要求強一致與低延遲，拆服務只會把本地耦合變成網路耦合。模組化應先在同一 JVM 與同一資料庫內完成。

### 3. 伺服器是唯一規則權威

前端可以做提示與預覽，但不能維護另一套完整合法性規則。伺服器應提供 viewer-specific `actionCapabilities`，NPC 也使用同一份 capabilities。

### 4. action log 先做 audit/replay log，不直接宣稱 event sourcing

目前真實狀態仍在 normalized tables。下一階段先確保：

- 每個 accepted command 有唯一 ID。
- 每批 mutation 有 stateVersion。
- action/event log 記錄足以診斷與 deterministic replay test。

在能用 log 完整重建所有狀態前，不把系統標示為 event-sourced。

### 5. 效果文字解析應移到資料匯入期

對戰 runtime 不應以日文自然語言 regex 作主要規則來源。目標是：

- import/admin 時將文字編譯成版本化 typed effect plan。
- match start snapshot 固定 card/ruleset version。
- runtime 只執行已驗證 plan。
- 未遷移卡透過明確 legacy adapter 執行並產生指標。

## 三、架構決策紀錄

| ID | 決策 | 理由 |
| --- | --- | --- |
| ADR-001 | 採 modular monolith | 保留本地交易，先解決責任與依賴方向 |
| ADR-002 | REST command + WebSocket server event | 現有基礎成熟，瀏覽器支援簡單 |
| ADR-003 | command 必帶 `commandId` 與 `expectedStateVersion` | 防雙擊、重送與 stale action |
| ADR-004 | 每場對戰保存 `rulesetVersion`、`cardDataVersion`、`rngSeed` | 可重播、可處理卡片勘誤與版本差異 |
| ADR-005 | pending decision/interaction 收斂為 `PendingChoice` domain model | 互動本質都是暫停後續接 |
| ADR-006 | rule validation 與 effect execution 分離 | 「能不能做」與「做了會發生什麼」分開測試 |
| ADR-007 | server projection 保護 hidden information | 玩家、對手、觀戰者不能共用同一 DTO |
| ADR-008 | 不先引入 Redis、message broker 或前端全域狀態套件 | 先建立清楚介面，再以量測決定基礎設施 |
| ADR-009 | Legacy facade 設定 no-growth budget | 新 service 必須移除舊 ownership/依賴，避免只把 God Class 變成 delegate hub |
| ADR-010 | Recovery baseline 是所有新工作包的硬性前置 | 久未維護的工作樹先完成、回滾或隔離，避免在未知狀態疊加重構 |
| ADR-011 | 不再為每個 extraction 建 acceptance review | work item、commit、測試輸出與 live status 已足以提供可追溯證據 |

## 四、優化成功指標

### 結構

- 新公開 action 只需新增 command/handler、rule/capability 與測試，不直接擴充 God Class。
- `match` 模組以 application/domain/infrastructure/readmodel 分層，跨模組依賴可由 architecture test 驗證。
- `MatchActionService`、`MatchEffectService` 最終只作相容 facade 或移除。

### 正確性

- duplicate command 不會重複扣資源或多寫 action。
- stale command 回傳可識別衝突與最新版本。
- 同 seed + 初始 snapshot + accepted commands 產生相同結果。
- 所有 projection 有 hidden-information leak 測試。

### 開發體驗

- 每個工作包可在一個小 commit 或數個同主題 commit 完成。
- 新卡在 import 時就能知道 unsupported primitive，而不是進對戰後才失敗。
- 測試可依 action family 執行，不需定位 32,000 行單檔。

### 執行效能

- 正常 WebSocket 連線時不再常態 1.5 秒輪詢。
- action response 或隨後事件可讓 client 判斷 stateVersion 是否連續。
- GameRoom 不再對每張已知卡逐一發送 detail request。

## 五、明確非目標

- 本輪不拆 microservices。
- 本輪不改寫成純 event sourcing。
- 本輪不一次搬完所有 package。
- 本輪不一次遷移全部官方卡。
- 本輪不以行數為唯一 KPI。
- 本輪不在沒有量測前導入 Redis、Kafka 或複雜前端 state library。
