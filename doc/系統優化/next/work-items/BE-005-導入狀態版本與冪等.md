# BE-005：導入狀態版本與冪等

狀態：READY_AFTER_BE-003
風險：高
Repository：`hololive-cardgame-backend`
建議 commit：`後端：導入對戰狀態版本與指令冪等`
前置工作：BE-001、BE-003

## 一、目標

建立每場對戰單調 `stateVersion` 與 command receipt，先讓經過 `MatchCommandGateway` 的 pilot command 支援：

- `commandId`
- `expectedStateVersion`
- duplicate result replay
- stale state rejection
- commit 後 publish

## 二、必讀

- `doc/系統優化/next/03-同步回放與觀測藍圖.md`
- `doc/0212-併發鎖策略與效能優化.md`
- `MatchEntity` / `matches` migration
- `MatchActionEntity` / `match_actions`
- `MatchRepository.findByIdForUpdate`
- End Turn 既有 idempotency 實作與 contracts
- `MatchSocketHandler`

此工作含 DB、公開 contract 與併發語意，實作前先回報 migration、相容與 rollback/forward-fix。

## 三、範圍內

資料：

- `matches.state_version BIGINT NOT NULL DEFAULT 0`
- command receipt table，至少 unique `(match_id, command_id)`
- payload hash、status、previous/new version、result/error、timestamps

應用：

- command envelope。
- expected-version check。
- duplicate check。
- version bump。
- after-commit publish。

API：

- 先以 additive header/body/response 欄位支援。
- 舊 client 無 version 時可走 compatibility mode，但要記 metric，且不可宣稱具備冪等。

## 四、非目標

- 不建立 Kafka。
- 不把 Redis 當 canonical state。
- 不把整個系統改成 event sourcing。
- 不一次遷移所有 endpoint；pilot 範圍必須在開始前列明。
- 不在同批改核心 action 規則。

## 五、交易順序

固定：

1. authenticate/authorize。
2. begin transaction。
3. `SELECT match FOR UPDATE`。
4. 查 `(matchId, commandId)`。
5. duplicate：驗證 payload hash並回原結果。
6. 比對 expected version。
7. handler 執行。
8. 寫 action/events。
9. bump version。
10. 寫 receipt result。
11. commit。
12. after-commit publish versioned snapshot/event。

任何 4 到 10 的錯誤都不得留下部分成功 receipt。

## 六、執行步驟

1. 建 forward-only Flyway migration。
2. persistence adapter tests 驗證 unique/lock。
3. command gateway 加 compatibility-aware envelope。
4. pilot command 接 version/idempotency。
5. response/GameState/WebSocket 加 additive `stateVersion`。
6. controller publish 移到 after-commit application event 或 publisher port。
7. 補 concurrency tests：
   - 相同 commandId 同 payload。
   - 相同 commandId 不同 payload。
   - 兩個不同 command 同 expected version。
   - publish failure 不回滾已 commit command。

## 七、驗收

- duplicate 成功 command 不重複 mutation/action log/version bump。
- stale command 回明確 error 與 currentVersion。
- version 只在 accepted state-changing command 增加。
- WebSocket snapshot 與 REST result version 一致。
- publish 發生在 commit 後。
- 舊 client 在 compatibility window 可使用，但 log/metric 可識別。
- migration 可套用到有既有 matches 的 DB。

## 九、回滾與部署

採 expand/contract：

1. 先部署 additive columns/table 與 server compatibility。
2. 再部署新 client。
3. 觀察 legacy-command metric。
4. 最後才考慮強制 commandId/version。

不可用 destructive rollback 刪 receipt。若應用需回退，保留 schema，舊版應忽略新 table/column。
