# 遷移路線與工作包索引

更新日期：2026-09-03
定位：唯一的 live execution plan、狀態表與風險閘門

## 一、執行策略

採 recovery-first vertical slice strangler：

1. 先完成或回滾既有工作樹，不在未知基線上疊新架構。
2. 保持 REST/WS/DB 相容，在 facade 後建立 typed application seam。
3. 一次遷移一個 command/action family，先測試、再搬 ownership、最後刪舊責任。
4. 共享規則先收斂成 rule/fact，capability、handler、NPC 共用。
5. 每批都要有可回滾點，不以大規模 package move 製造完成感。
6. state version、typed effect、replay 等跨切面能力必須遵守前置順序。

### Legacy facade budget

從本計畫生效起：

- `MatchActionService` 與 `MatchEffectService` 不新增新的 feature responsibility。
- 每個完成的 production slice 至少移除一段舊 orchestration、重複規則或依賴。
- 若檔案行數下降但依賴數上升，視為未完成 ownership 遷移。
- 高風險卡號特例不得直接加進主 service；需有 legacy adapter、測試與移除條件。

### R5：replay、測試拆分與 NPC

- BE-006 ReplayHarness/測試巨檔。

完成條件：

- 32,000 行測試依 turn/choice/attack/effect/projection 漸進搬移。

## 五、commit 與 worktree 規則

### 建議先整理的 commit

1. `文件：重新基準化系統優化計畫`
2. `文件：加入 GitNexus 協作規範`
3. `後端：提供回合合法操作能力投影`

實際 commit 前仍需檢查檔案歸屬；不要把 `.gitignore`、代理規範、整套藍圖與 BE-002 production code 混在一個 commit。

### 同時工作限制

- 同一工作樹一次只做一份 work item。
- BE-007、BE-003、BE-005 都可能碰 `MatchActionService`；不可在同一 checkout 平行修改。
- 前後端可分別工作，但公開 DTO/WS contract 的 producer/consumer 需有明確版本與合併順序。
- 文件 discovery 可以平行，介面決策由前置工作包先完成。

## 六、每批固定輸出

- scope 與非目標。
- GitNexus upstream impact；HIGH/CRITICAL 先說明風險。
- characterization/contract 與 focused integration。
- legacy responsibility/dependency 實際減少項目。
- API/DB/規則相容與 rollback。
- GitNexus detect changes。
- 更新本狀態表與 work item。
- 繁體中文 commit 建議。

## 七、停止條件

遇到以下情況停止擴大範圍：

- 同批需要改 DB schema、公開 DTO、核心 timing 與前端 UI。
- 新舊 pipeline 對同一 command 的 state/event 不一致。
- capability enabled 但相同 fixture 的 command 被相同 precondition 拒絕。
- hidden projection 出現資訊外洩。
- 新服務只增加轉送層，沒有移除舊責任。
- lint/test 基線仍紅卻開始大量 component move。
- GitNexus HIGH/CRITICAL 影響尚未有 focused test 與 rollback。

## 八、暫不執行

- microservices、Kafka、Redis、CQRS 全面改造。
- 一次性 package 大搬家。
- 完整 event sourcing。
- 一次遷移全部官方卡或全部 effect family。
- 在沒有 state version 前移除 polling fallback。
- 在沒有 scenario fixture 前大量搬動測試巨檔。
