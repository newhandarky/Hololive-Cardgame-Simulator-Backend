# 資料庫設計補充：卡片實例層與索引策略

## 概述

本文件補充先前資料庫設計的「卡片實例層」概念，以及資料表的唯一約束與索引策略，確保資料一致性與查詢效能。

---

## 1. 卡片設計的三層架構

### 1.1 概念說明

在 HOLOLIVE 卡牌遊戲中，「卡片」有三個層次：

```
卡片定義層（Card Definition）
    ↓ 玩家持有
卡片持有層（Card Ownership）
    ↓ 進入對戰
卡片實例層（Card Instance）
```

#### 層次說明

| 層次 | 資料表 | 說明 | 範例 |
|-----|-------|------|------|
| **卡片定義層** | `cards`, `oshi_cards`, `member_cards`, `support_cards`, `cheer_cards` | 定義遊戲中的所有卡片（全域共用） | "推しペコラ" 這張卡的基本資訊 |
| **卡片持有層** | `user_cards` | 玩家持有的卡片（玩家的卡包） | 玩家 A 有 3 張 "推しペコラ" |
| **卡片實例層** | `match_cards`, `match_holomems`, `match_holopower` | 對戰中的卡片實例（每場對戰獨立） | 對戰 #42 中，玩家 A 手牌中的第 2 張 "推しペコラ" |

---

### 1.2 為什麼需要「卡片實例層」？

#### 問題情境

假設沒有「實例層」，只記錄 `card_id`：
- 玩家 A 手牌有 2 張同名卡 "ホロメンA"
- 玩家打出其中一張 → 如何知道打的是哪一張？
- 場上有 2 隻同名ホロメン → 如何區分它們的狀態（傷害、エール、橫置狀態）？

#### 解決方案

每張進入對戰的卡片都給予一個 **唯一實例 ID**，例如：
- `match_cards.id = 1001`：對戰中的某張具體卡片
- `match_holomems.id = 501`：場上的某隻具體ホロメン

這樣即使是同名卡，也能透過實例 ID 區分。

## 2. 卡片實例層設計

### 2.1 `match_cards`（對戰中的卡片追蹤）

這是「所有卡片在對戰中的位置追蹤表」，包括：
- 手牌
- 牌庫
- エールデッキ
- アーカイブ
- LIFE 區

```sql
CREATE TABLE match_cards (
    id SERIAL PRIMARY KEY,  -- ⚠️ 卡片實例 ID（唯一識別）
    
    match_id INT NOT NULL REFERENCES matches(id) ON DELETE CASCADE,
    owner_user_id INT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    
    card_id VARCHAR(50) NOT NULL REFERENCES cards(card_id),  -- 指向卡片定義
    
    -- 當前所在區域
    zone VARCHAR(20) NOT NULL
      CONSTRAINT chk_match_card_zone
        CHECK (zone IN ('DECK', 'HAND', 'CHEER_DECK', 'HOLOPOWER', 'STAGE', 'ARCHIVE', 'LIFE')),
    
    -- 順序（用於牌庫／手牌排序）
    order_index INT,
    
    -- 表／裏
    is_face_down BOOLEAN NOT NULL DEFAULT TRUE,
    
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);

-- 索引策略（見下文）
CREATE INDEX idx_match_cards_match_owner_zone 
    ON match_cards(match_id, owner_user_id, zone);

CREATE INDEX idx_match_cards_match_zone 
    ON match_cards(match_id, zone);
```

#### 重點說明

- **單一真實來源（Single Source of Truth）**：
  - `match_cards` 是「所有卡片位置」的唯一真實來源
  - 其他表（如 `match_holomems`）只記錄「場上角色的額外狀態」，不重複記錄位置

- **zone 的意義**：
  - `DECK`：主牌庫（メインデッキ）
  - `HAND`：手牌
  - `CHEER_DECK`：エールデッキ
  - `HOLOPOWER`：ホロパワーゾーン
  - `STAGE`：場上（詳細位置由 `match_holomems` 記錄）
  - `ARCHIVE`：アーカイブ（棄牌區）
  - `LIFE`：推しライフ區

---

### 2.2 `match_holomems`（場上ホロメン的狀態）

這是「場上角色的詳細狀態表」，**不重複記錄位置**，只記錄場上才有的狀態。

```sql
CREATE TABLE match_holomems (
    id SERIAL PRIMARY KEY,  -- ⚠️ ホロメン 實例 ID
    
    match_id INT NOT NULL REFERENCES matches(id) ON DELETE CASCADE,
    owner_user_id INT NOT NULL REFERENCES users(id),
    
    -- ⚠️ 指向 match_cards 的實例 ID（而非 card_id）
    match_card_id INT NOT NULL REFERENCES match_cards(id) ON DELETE CASCADE,
    
    card_id VARCHAR(50) NOT NULL REFERENCES member_cards(card_id),  -- 冗餘但方便查詢
    
    -- 場上位置（更精細）
    zone VARCHAR(20) NOT NULL
      CONSTRAINT chk_holomem_zone
        CHECK (zone IN ('CENTER', 'COLLAB', 'BACK')),
    
    -- 狀態
    is_rested BOOLEAN NOT NULL DEFAULT FALSE,  -- 橫置狀態
    is_face_down BOOLEAN NOT NULL DEFAULT FALSE,
    damage_taken INT NOT NULL DEFAULT 0,  -- 累積傷害
    
    -- 當前等級（若有 Bloom）
    current_level VARCHAR(20) NOT NULL
      CONSTRAINT chk_holomem_current_level
        CHECK (current_level IN ('DEBUT', 'FIRST', 'SECOND')),
    
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    
    -- ⚠️ 唯一約束：同一對戰中，同一 match_card_id 只能有一筆記錄
    UNIQUE (match_id, match_card_id)
);

-- 索引策略
CREATE INDEX idx_match_holomems_match_owner_zone 
    ON match_holomems(match_id, owner_user_id, zone);

CREATE INDEX idx_match_holomems_match_zone 
    ON match_holomems(match_id, zone);
```

#### 重點說明

- **關聯到 `match_cards`**：
  - `match_card_id` 指向 `match_cards.id`（實例 ID）
  - 這樣可以追蹤「這隻ホロメン 對應的卡片實例」

- **單一真實來源**：
  - 卡片位置由 `match_cards.zone` 記錄（`STAGE`）
  - 場上精細位置由 `match_holomems.zone` 記錄（`CENTER` / `COLLAB` / `BACK`）

- **資料一致性檢查**：
  - 當ホロメン進入場上：
    1. `match_cards.zone = 'STAGE'`
    2. 建立 `match_holomems` 記錄，設定 `zone = 'CENTER'` 或 `BACK`
  - 當ホロメン離場：
    1. 刪除 `match_holomems` 記錄
    2. `match_cards.zone = 'ARCHIVE'`

### 2.3 `match_holopower`（ホロパワー的追蹤）

這是「ホロパワー的實例追蹤表」。

```sql
CREATE TABLE match_holopower (
    id SERIAL PRIMARY KEY,  -- ⚠️ ホロパワー 實例 ID
    
    match_id INT NOT NULL REFERENCES matches(id) ON DELETE CASCADE,
    owner_user_id INT NOT NULL REFERENCES users(id),
    
    -- ⚠️ 指向 match_cards 的實例 ID
    match_card_id INT NOT NULL REFERENCES match_cards(id) ON DELETE CASCADE,
    
    card_id VARCHAR(50) NOT NULL REFERENCES cards(card_id),  -- 冗餘但方便
    
    -- 狀態：裏面（未使用）或表面（已使用但還沒送到アーカイブ）
    is_face_up BOOLEAN NOT NULL DEFAULT FALSE,
    
    -- 順序（如果需要記錄放置順序）
    order_index INT,
    
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    
    -- ⚠️ 唯一約束：同一對戰中，同一 match_card_id 只能有一筆記錄
    UNIQUE (match_id, match_card_id)
);

-- 索引策略
CREATE INDEX idx_match_holopower_match_owner 
    ON match_holopower(match_id, owner_user_id);

CREATE INDEX idx_match_holopower_match_owner_faceup 
    ON match_holopower(match_id, owner_user_id, is_face_up);
```

#### 重點說明

- **關聯到 `match_cards`**：
  - `match_card_id` 指向 `match_cards.id`
  - 當卡片進入ホロパワーゾーン：
    1. `match_cards.zone = 'HOLOPOWER'`
    2. 建立 `match_holopower` 記錄

- **單一真實來源**：
  - `match_cards` 記錄「這張卡在ホロパワーゾーン」
  - `match_holopower` 記錄「這張ホロパワー的狀態（裏面／表面）」

## 3. 唯一約束與索引策略

### 3.1 唯一約束（Unique Constraints）

以下是關鍵的唯一約束：

| 資料表 | 唯一約束 | 說明 |
|-------|---------|------|
| `users` | `line_user_id` | 一個 LINE 帳號只能綁定一個系統帳號 |
| `matches` | `room_code` | 房間代碼不可重複 |
| `match_holomems` | `(match_id, match_card_id)` | 同一對戰中，同一卡片實例只能有一筆場上記錄 |
| `match_holopower` | `(match_id, match_card_id)` | 同一對戰中，同一卡片實例只能有一筆ホロパワー記錄 |
| `user_cards` | `(user_id, card_id)` | 同一玩家對同一卡片只能有一筆持有記錄（數量用 `count`） |

---

### 3.2 索引策略（Index Strategy）

#### 3.2.1 `match_cards` 索引

```sql
-- 查詢「某對戰中，某玩家的某區域卡片」
CREATE INDEX idx_match_cards_match_owner_zone 
    ON match_cards(match_id, owner_user_id, zone);

-- 查詢「某對戰中，某區域的所有卡片」（不分玩家）
CREATE INDEX idx_match_cards_match_zone 
    ON match_cards(match_id, zone);

-- 查詢「某對戰中的所有卡片」（用於重建狀態）
CREATE INDEX idx_match_cards_match 
    ON match_cards(match_id);
```

**查詢範例**：
```sql
-- 查詢玩家 A 的手牌
SELECT * FROM match_cards 
WHERE match_id = 42 
  AND owner_user_id = 101 
  AND zone = 'HAND'
ORDER BY order_index;

-- 查詢雙方玩家的場上卡片
SELECT * FROM match_cards 
WHERE match_id = 42 
  AND zone = 'STAGE';
```

---

#### 3.2.2 `match_holomems` 索引

```sql
-- 查詢「某對戰中，某玩家的場上ホロメン」
CREATE INDEX idx_match_holomems_match_owner 
    ON match_holomems(match_id, owner_user_id);

-- 查詢「某對戰中，某玩家的某位置ホロメン」
CREATE INDEX idx_match_holomems_match_owner_zone 
    ON match_holomems(match_id, owner_user_id, zone);

-- 查詢「某對戰中的所有場上ホロメン」
CREATE INDEX idx_match_holomems_match 
    ON match_holomems(match_id);
```

**查詢範例**：
```sql
-- 查詢玩家 A 的センターホロメン
SELECT * FROM match_holomems 
WHERE match_id = 42 
  AND owner_user_id = 101 
  AND zone = 'CENTER';

-- 查詢對戰中所有アクティブ狀態的ホロメン
SELECT * FROM match_holomems 
WHERE match_id = 42 
  AND is_rested = FALSE;
```

---

#### 3.2.3 `match_actions` 索引

```sql
-- 查詢「某對戰的所有動作」（按回合與順序排序）
CREATE INDEX idx_match_actions_match_turn_order 
    ON match_actions(match_id, turn_number, action_order);

-- 查詢「某對戰的某回合動作」
CREATE INDEX idx_match_actions_match_turn 
    ON match_actions(match_id, turn_number);
```

**查詢範例**：
```sql
-- 取得對戰的所有動作（用於重建狀態）
SELECT * FROM match_actions 
WHERE match_id = 42 
ORDER BY turn_number, action_order;

-- 取得第 3 回合的所有動作
SELECT * FROM match_actions 
WHERE match_id = 42 
  AND turn_number = 3 
ORDER BY action_order;
```

---

#### 3.2.4 `match_holopower` 索引

```sql
-- 查詢「某對戰中，某玩家的ホロパワー」
CREATE INDEX idx_match_holopower_match_owner 
    ON match_holopower(match_id, owner_user_id);

-- 查詢「某對戰中，某玩家的裏面ホロパワー」（用於檢查可用數量）
CREATE INDEX idx_match_holopower_match_owner_faceup 
    ON match_holopower(match_id, owner_user_id, is_face_up);
```

**查詢範例**：
```sql
-- 查詢玩家 A 有多少張裏面的ホロパワー（可用）
SELECT COUNT(*) FROM match_holopower 
WHERE match_id = 42 
  AND owner_user_id = 101 
  AND is_face_up = FALSE;
```

---

#### 3.2.5 `match_holomem_cheers` 索引

```sql
-- 查詢「某ホロメン附著的エール」
CREATE INDEX idx_match_holomem_cheers_holomem 
    ON match_holomem_cheers(match_holomem_id);
```

**查詢範例**：
```sql
-- 查詢某ホロメン的所有エール
SELECT c.color 
FROM match_holomem_cheers mhc
JOIN cheer_cards c ON mhc.cheer_card_id = c.card_id
WHERE mhc.match_holomem_id = 501;

-- 統計某ホロメン各顏色エール數量
SELECT c.color, COUNT(*) as count
FROM match_holomem_cheers mhc
JOIN cheer_cards c ON mhc.cheer_card_id = c.card_id
WHERE mhc.match_holomem_id = 501
GROUP BY c.color;
```

## 4. 資料一致性檢查

### 4.1 卡片位置一致性

確保 `match_cards` 與其他表的一致性：

#### 規則

1. **場上ホロメン**：
   - `match_cards.zone = 'STAGE'`
   - 必須存在對應的 `match_holomems` 記錄
   - 反之亦然：`match_holomems` 存在 → `match_cards.zone = 'STAGE'`

2. **ホロパワー**：
   - `match_cards.zone = 'HOLOPOWER'`
   - 必須存在對應的 `match_holopower` 記錄
   - 反之亦然

3. **其他區域**（HAND / DECK / ARCHIVE 等）：
   - 只在 `match_cards` 記錄
   - 不會有對應的 `match_holomems` 或 `match_holopower`

#### 一致性檢查 SQL

```sql
-- 檢查：場上ホロメン 必須在 match_cards 中標記為 STAGE
SELECT mh.id 
FROM match_holomems mh
LEFT JOIN match_cards mc ON mh.match_card_id = mc.id
WHERE mc.zone != 'STAGE' OR mc.id IS NULL;

-- 檢查：ホロパワー 必須在 match_cards 中標記為 HOLOPOWER
SELECT mhp.id 
FROM match_holopower mhp
LEFT JOIN match_cards mc ON mhp.match_card_id = mc.id
WHERE mc.zone != 'HOLOPOWER' OR mc.id IS NULL;

-- 檢查：zone = STAGE 的卡片必須有對應的 match_holomems
SELECT mc.id 
FROM match_cards mc
LEFT JOIN match_holomems mh ON mc.id = mh.match_card_id
WHERE mc.zone = 'STAGE' AND mh.id IS NULL;
```

---

### 4.2 對戰狀態一致性

#### 檢查點

1. **手牌數量**：
   - `match_cards` 中 `zone = 'HAND'` 的數量 = 玩家實際手牌數

2. **場上ホロメン數量**：
   - センター：最多 1 隻
   - コラボ：最多 1 隻
   - バック：最多 5 隻

3. **LIFE 數量**：
   - `match_players.current_life` = `match_cards` 中 `zone = 'LIFE'` 的數量

#### 一致性檢查 SQL

```sql
-- 檢查：センター 不可超過 1 隻
SELECT match_id, owner_user_id, COUNT(*) as center_count
FROM match_holomems
WHERE zone = 'CENTER'
GROUP BY match_id, owner_user_id
HAVING COUNT(*) > 1;

-- 檢查：バック 不可超過 5 隻
SELECT match_id, owner_user_id, COUNT(*) as back_count
FROM match_holomems
WHERE zone = 'BACK'
GROUP BY match_id, owner_user_id
HAVING COUNT(*) > 5;

-- 檢查：LIFE 數量是否一致
SELECT mp.match_id, mp.user_id, 
       mp.current_life as expected,
       COUNT(mc.id) as actual
FROM match_players mp
LEFT JOIN match_cards mc ON mp.match_id = mc.match_id 
                          AND mp.user_id = mc.owner_user_id 
                          AND mc.zone = 'LIFE'
GROUP BY mp.match_id, mp.user_id, mp.current_life
HAVING mp.current_life != COUNT(mc.id);
```

## 5. 從動作記錄重建狀態

### 5.1 重建邏輯

當玩家斷線重連或需要驗證狀態時，從 `match_actions` 重建：

```java
public MatchState rebuildStateFromActions(Long matchId) {
    // 1. 取得對戰初始狀態
    Match match = matchRepository.findById(matchId)
        .orElseThrow(() -> new RuntimeException("對戰不存在"));
    
    // 2. 取得所有動作記錄（按順序）
    List<MatchAction> actions = matchActionRepository
        .findByMatchIdOrderByTurnNumberAscActionOrderAsc(matchId);
    
    // 3. 初始化空白狀態
    MatchState state = new MatchState(match);
    
    // 4. 依序執行每個動作
    for (MatchAction action : actions) {
        applyActionToState(state, action);
    }
    
    // 5. 回傳重建後的狀態
    return state;
}
```

---

### 5.2 狀態驗證

重建後的狀態應與資料庫中的狀態一致：


## 6. 效能最佳化建議

### 6.1 批次查詢

避免 N+1 查詢問題：

```java
// ❌ 不好的做法（N+1）
List<MatchHolomem> holomems = matchHolomemRepository.findByMatchId(matchId);
for (MatchHolomem holomem : holomems) {
    List<CheerCard> cheers = matchHolomemCheerRepository
        .findByMatchHolomemId(holomem.getId());  // N 次查詢
}

// ✅ 好的做法（JOIN）
@Query("SELECT mh FROM MatchHolomem mh " +
       "LEFT JOIN FETCH mh.cheers " +
       "WHERE mh.matchId = :matchId")
List<MatchHolomem> findByMatchIdWithCheers(@Param("matchId") Long matchId);
```
